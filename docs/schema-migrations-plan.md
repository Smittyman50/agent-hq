# Plan: schema migrations with Alembic

Status: implemented (2026-11-14). How to use it: [schema-migrations.md](schema-migrations.md).
Where the build departed from this plan:

- Fresh databases run every revision instead of `create_all()` + stamp. It costs about 0.05 s,
  and a database built from the models at that moment would hide a model change that has no
  revision (autogenerate would then find nothing to write).
- So the baseline `0001` is a full autogenerated `create_table` revision, not an empty marker.
- Added an autogenerate hook (`app/migrations/filters.py`): a new NOT NULL column gets the
  model's plain default as a database default, which is what the old back-fill did.
- Postgres was not dumped automatically, as planned; SQLite backups keep the last 5.

The original plan follows.

Status: draft, not started. Tracks the README item "Schema migrations: new columns on existing
tables are added automatically at startup; add Alembic once you need renames or data changes."

## Where things stand today

`backend/app/db.py:init_db()` runs on every start of the API (`main.py` lifespan), every worker
(`worker.py:run_worker`), the account CLI (`python -m app.auth`) and the tests. It does four things:

1. `SQLModel.metadata.create_all()`: creates missing tables.
2. `add_missing_columns()`: `ALTER TABLE ... ADD COLUMN` for model columns the table lacks, then
   back-fills the column's Python default.
3. `add_missing_enum_values()`: Postgres only, `ALTER TYPE ... ADD VALUE` for new enum members.
4. `memory.init_storage()` / `knowledge.init_storage()`: Postgres + pgvector only, adds
   `memory.embedding_vec`, `knowledgechunk.embedding_vec` and the `memory_fts` / `knowledgechunk_fts`
   GIN indexes. None of these are in the SQLModel metadata.

What this cannot do: rename or drop a column or table, change a type or nullability, add a
constraint or index to an existing table, or move data. That is the gap Alembic fills.

Things the plan has to respect:

- **Two backends.** SQLite (default, `data_dir/agent_hq.db`) and Postgres (`AHQ_DB_URL`). SQLite
  can't alter columns in place, so migrations must use Alembic's batch mode.
- **Many processes start at once.** `hq`, `worker`, `worker-desktop` and any worker replicas on
  other hosts all call `init_db()` against the same Postgres. Today that's safe because every step
  is idempotent; migrations are not, so they need a lock.
- **Mixed versions across hosts.** A worker on another machine can run an older image than `hq`.
- **Tables Alembic must not own.** LangGraph's checkpointer tables (`checkpoints`,
  `checkpoint_blobs`, `checkpoint_writes`, `checkpoint_migrations`) live in the same Postgres
  database and manage themselves; the pgvector columns and FTS indexes are added outside the
  models. Autogenerate would otherwise propose dropping all of them.
- **Packaging.** The Dockerfile copies only `backend/app` and does a non-editable `pip install .`,
  with packages found by `include = ["app*"]`. Migration scripts must therefore live inside the
  `app` package and be importable packages, or they won't be in the image.

## Design

### Layout

```
backend/
  alembic.ini                 # dev convenience only: script_location = app:migrations
  app/
    migrate.py                # run_migrations(), check_revision(), small CLI
    migrations/
      __init__.py
      env.py                  # target_metadata = SQLModel.metadata, filters, batch mode
      script.py.mako          # template; adds `import sqlmodel` so AutoString renders
      versions/
        __init__.py
        0001_baseline.py      # empty upgrade(): marks "schema as of the Alembic switch"
```

`app/migrate.py` builds the Alembic `Config` in code (`script_location="app:migrations"`,
`sqlalchemy.url` from `settings.db_url`), so nothing at runtime depends on `alembic.ini` or the
current directory. Add `alembic>=1.13` to dependencies and `script.py.mako` to package data
(`[tool.setuptools.package-data] app = ["migrations/*.mako"]`) so `revision` works from an
installed copy too.

### env.py essentials

- `target_metadata = SQLModel.metadata` after `from app import models`.
- `render_as_batch=True` when the dialect is SQLite (column renames/alters via table copy).
- `compare_type=True`, `compare_server_default=False` (server defaults aren't used; Python defaults are).
- `include_name` / `include_object` filter that skips: tables not in the metadata (LangGraph's
  checkpoint tables, `alembic_version`), the `embedding_vec` columns, and the `*_fts` indexes.
- Use the app's existing engine (`db.engine()`) via `connectable = config.attributes.get("connection")`
  so tests that `reset_engine()` to a temp DB get migrated, not the default file.

### Startup flow (replaces the body of `init_db()`)

```
init_db():
    with migration_lock():                      # see below
        state = detect()                        # empty | legacy (tables, no alembic_version) | versioned
        if state == empty:
            create_all(); stamp(head)           # fresh install: build straight from the models
        elif state == legacy:
            add_missing_columns()               # the existing code, one last time
            stamp("0001_baseline")
            upgrade(head)
        else:
            upgrade(head)
        add_missing_enum_values()               # kept: additive, idempotent, needs AUTOCOMMIT
    memory.init_storage(); knowledge.init_storage()   # unchanged
```

Notes on each branch:

- **Fresh install** builds from the models and stamps head rather than replaying every revision.
  It's faster, and data migrations have nothing to act on in an empty database. The test below
  guarantees the two paths produce the same schema.
- **Legacy** databases (every install that exists today) are brought up to the baseline by the
  current auto-add code, then stamped. Because `0001_baseline` is defined as "today's models", this
  is exact. After the release that ships Alembic, `add_missing_columns()` is only reachable from
  this branch.
- **Why auto-add must stop for versioned DBs:** if a later revision renames `foo` to `bar`, the
  auto-add would see `bar` missing and create it empty before the rename runs, and the rename
  would then fail. From the switch onward, every schema change (including plain new columns) is a
  revision. The README line changes accordingly.
- **Enum values** stay on the existing helper: Alembic autogenerate doesn't detect new members of
  a Postgres native enum, and `ADD VALUE` can't run inside the migration transaction anyway.
- **pgvector/FTS** stay in `init_storage()` for now; they're conditional on the extension being
  available, which suits runtime code better than a revision. They could move into a
  Postgres-only revision later if they ever need altering.

### Who migrates, and the lock

- **Lock.** Postgres: `pg_advisory_lock(<fixed 64-bit key>)` on a dedicated connection held for
  the whole of the flow above, then `pg_advisory_unlock`. SQLite: an exclusive `fcntl`/`msvcrt`
  lock on `data_dir/.migrate.lock` (SQLite is single-host, so a file lock is enough). A second
  process blocks, then finds nothing left to do.
- **Version skew.** `check_revision()` runs after the lock in every process:
  - DB at this code's head: carry on.
  - DB behind head: migrate (the flow above).
  - DB at a revision this code doesn't know (a newer `hq` already migrated): log a clear error
    naming both revisions and exit non-zero, so an old worker restarts in a loop instead of
    writing rows with an outdated idea of the schema. An env override
    (`AHQ_ALLOW_SCHEMA_AHEAD=1`) lets a known-compatible additive change through.
- Optional setting `AHQ_MIGRATE_ON_START` (default `1`). With `0`, the process only checks and
  waits (poll up to ~60 s for the DB to reach its head, then exit). Useful if you'd rather only
  `hq` migrates and remote workers never touch the schema.

### Backups before migrating

- SQLite: before any `upgrade` that will apply at least one revision, copy the DB file to
  `data_dir/backups/agent_hq-<old_rev>-<timestamp>.db` (use SQLite's online backup API, not a raw
  file copy). Keep the last 5.
- Postgres: no automatic dump (it's shared infra in `deploy/infra`); the upgrade notes in the
  README say to `pg_dump` first, and `python -m app.migrate status` shows pending revisions so you
  can decide before restarting `hq`.

### Developer workflow

```
cd backend
python -m app.migrate revision -m "rename agent.pool to agent.pool_name"   # autogenerate
python -m app.migrate status        # current DB revision, head, pending list
python -m app.migrate upgrade       # manual upgrade (same lock as startup)
python -m app.migrate stamp <rev>   # escape hatch
```

`alembic` itself also works from `backend/` via `alembic.ini`. Policy for revisions:

- Forward-only in practice. Write `downgrade()` when it's trivial; otherwise raise
  `NotImplementedError` and rely on the backup.
- Never import `app.models` in a revision. Use `sa.table()`/`sa.column()` stubs for data moves,
  so old revisions keep working after the models change.
- Data changes in batches (`UPDATE ... WHERE id IN (SELECT ... LIMIT 1000)`) if a table can be
  large (memories, knowledge chunks, events).
- Review every autogenerated file: autogenerate guesses a rename as drop+add, and that loses data.
  Replace with `op.alter_column(..., new_column_name=...)` (batch mode on SQLite).
- Name revisions `NNNN_short_slug.py` with `rev_id` set to `NNNN` so the history reads in order.

## Tests (backend/tests/test_migrations.py)

1. **Fresh = upgraded.** Empty SQLite DB: `create_all` + stamp head, versus stamp baseline-era schema
   + `upgrade head`; compare with `alembic.autogenerate.compare_metadata`. Expect no diff. Same on
   Postgres via the existing `postgres_url` fixture.
2. **Models have a migration.** `upgrade head` on an empty DB, then `compare_metadata` against
   `SQLModel.metadata` must be empty. This is the test that fails when someone edits a model and
   forgets `migrate revision`; it replaces the safety net the auto-add used to provide.
3. **Legacy upgrade.** Build a DB with today's schema minus a couple of columns and no
   `alembic_version`; `init_db()` must add the columns, stamp baseline, and reach head.
4. **Idempotent.** `init_db()` twice is a no-op the second time (extends the existing check in
   `test_postgres.py`).
5. **Concurrent start (Postgres).** Two threads call `init_db()` at once against a fresh DB; both
   succeed, one migration run, one `alembic_version` row.
6. **Schema ahead.** Stamp an unknown revision; `init_db()` raises/exits with the documented message,
   and passes with `AHQ_ALLOW_SCHEMA_AHEAD=1`.
7. **Filters.** On Postgres with pgvector, after `init_storage()`, autogenerate shows no drops for
   `embedding_vec`, the FTS indexes or the LangGraph tables.
8. **A real rename with data** using a throwaway script directory in the test: add revision that
   renames a column and transforms values, run it on SQLite (batch mode) and Postgres, check rows.

Update `conftest.py` so the shared fixture goes through the new `init_db()` (it already calls it)
and `test_postgres.py`'s `drop_all` also drops `alembic_version`.

## Steps

1. Add `alembic` dependency, package data, `app/migrations/` skeleton, `env.py` with filters and
   batch mode, `script.py.mako` with `import sqlmodel`.
2. Generate `0001_baseline` against today's models; make its `upgrade()` empty and document why.
3. Write `app/migrate.py`: config builder, lock (Postgres advisory / SQLite file), `detect()`,
   `run_migrations()`, `check_revision()`, SQLite backup, CLI (`revision`, `status`, `upgrade`, `stamp`).
4. Rewrite `db.init_db()` to the flow above; keep `add_missing_columns()` (legacy branch only) and
   `add_missing_enum_values()`.
5. Add `AHQ_MIGRATE_ON_START` and `AHQ_ALLOW_SCHEMA_AHEAD` to `config.py` and `.env.example`.
6. Tests 1 to 8.
7. Docs: replace the README "Next steps" item; in the upgrade section, explain that schema changes
   are now revisions, how to make one, `pg_dump` before upgrading Postgres, where SQLite backups go,
   and what the "schema ahead" error means for workers on other hosts.
8. Verify in Docker: build the image, check `app/migrations/versions/*.py` are in site-packages,
   start `hq` + 2 worker replicas against an existing Postgres copy, confirm one stamp and clean logs.

Rough size: a day for 1 to 5, half a day for tests and docs.

## Open questions

- **Keep auto-add for plain new columns?** The plan retires it once a DB is versioned, so every
  change needs a revision (one command). The alternative is running `add_missing_columns()` after
  `upgrade head` and reserving revisions for renames and data moves. Less ceremony, but revisions
  can then never add a column themselves, test 2 can't exist, and models and migrations can
  quietly drift. Recommendation: retire it.
- **Should remote workers ever migrate?** Default here is yes (with the lock). Setting
  `AHQ_MIGRATE_ON_START=0` on worker hosts makes `hq` the only process that changes the schema.
- **Move pgvector columns and FTS indexes into revisions?** Not needed until one of them changes.
