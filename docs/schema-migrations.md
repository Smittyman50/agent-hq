# Schema migrations

Agent HQ keeps its database schema in Alembic revisions under `backend/app/migrations/versions/`.
Every process that opens the database (the API, each worker, `python -m app.auth`) brings it up
to date on startup, so upgrading is still "pull, rebuild, restart".

## What happens on startup

`db.init_db()` calls `migrate.ensure_schema()`, which takes a lock (a Postgres advisory lock, or
`data/.migrate.lock` next to a SQLite database) so that `hq` and the workers starting together
don't race, and then:

| The database is... | What happens |
|---|---|
| empty | every revision runs; the baseline (`0001`) creates all the tables |
| from before migrations (tables, no `alembic_version`) | the old add-missing-columns step catches it up, then it is stamped `0001` |
| behind this version | SQLite is backed up to `data/backups/`, then the pending revisions run |
| at this version | nothing |
| at a revision this version doesn't know | the process refuses to start (see below) |

After that, new values of Postgres enum types are still added automatically (Alembic can't detect
them), and the pgvector columns and full-text indexes are still set up by `memory.py` and
`knowledge.py`.

A database from before migrations can only be adopted by the release whose newest revision is
`0001`. If one turns up later, start that release once first, or, if you know its schema matches,
run `python -m app.migrate stamp 0001`.

## Commands

Run from `backend/` (or `docker compose exec hq python -m app.migrate ...`):

```
python -m app.migrate status                  # current revision, head, what's pending
python -m app.migrate upgrade                 # bring the database up to date now
python -m app.migrate revision -m "message"   # new revision, autogenerated from the models
python -m app.migrate revision -m "message" --empty   # blank revision for data-only changes
python -m app.migrate history
python -m app.migrate stamp <revision>        # mark the database as at a revision, run nothing
```

They use the database `AHQ_DB_URL` / `AHQ_DATA_DIR` point at. The plain `alembic` CLI also works
from `backend/` (`alembic.ini`), but it doesn't take the lock.

## Changing the schema

1. Make sure your dev database is current: `python -m app.migrate upgrade`.
2. Change the models in `app/models.py`.
3. `python -m app.migrate revision -m "what changed"`. This writes `NNNN_what_changed.py`.
4. **Read the file.** In particular:
   - **Renames come out as drop + add, which loses the data.** Replace them with
     `op.alter_column("table", "old", new_column_name="new")` inside
     `with op.batch_alter_table("table") as b:` (batch mode is what lets SQLite do it).
   - A new NOT NULL column gets the model's plain default as a database default, so it works on
     tables that already have rows. A field with a `default_factory` gets none: add a
     `server_default` or back-fill it in the revision.
   - Postgres enum types: autogenerate doesn't notice new values (startup adds them), and it
     doesn't drop removed ones.
5. Run the tests. `test_migrations.py::test_revisions_build_the_models_schema` fails if the
   models and the revisions disagree, so a forgotten revision shows up there.

Rules for revisions:

- Never import `app.models` in a revision; the models will have moved on by the time an old
  revision runs. For data changes use stubs: `sa.table("skill", sa.column("title", sa.String))`.
- Change large tables (memories, knowledge chunks, messages) in batches.
- `downgrade()` is optional. Write it when it's easy; otherwise raise `NotImplementedError` and
  rely on the backup. The baseline's downgrade always raises.
- Merge branches (two people adding a revision at once) with `alembic merge heads`; startup
  refuses to run with more than one head.

Autogenerate ignores what Agent HQ doesn't own through the models (`app/migrations/filters.py`):
LangGraph's checkpoint tables, the `embedding_vec` columns, and the `*_fts` indexes.

## Several machines

- **Workers on other hosts with an older image.** Once a newer `hq` has migrated the database, an
  older process finds a revision it doesn't know and exits with a message naming both revisions;
  update its image. If you know the change is compatible (say, a new nullable column), set
  `AHQ_ALLOW_SCHEMA_AHEAD=1` on it to start anyway.
- **Only `hq` should change the schema?** Set `AHQ_MIGRATE_ON_START=0` on the workers. They then
  wait (up to `AHQ_MIGRATE_WAIT_SECONDS`, default 120) for the database to reach their version and
  exit if it doesn't.

## Backups

- SQLite: before any upgrade or adoption, the database is copied to
  `data/backups/agent_hq-<old revision>-<time>.db` (SQLite's online backup). The last five are kept.
  To roll back, stop everything and copy one back over `data/agent_hq.db`.
- Postgres is shared infrastructure, so there's no automatic dump. Before pulling a version with
  pending revisions (`python -m app.migrate status` shows them), run
  `pg_dump -Fc agent_hq > agent_hq-$(date +%F).dump`.
